Languages and frameworks don't matter anymore

After 15+ years across Rails, Elixir, Node and React, why I think the stack matters less with AI agents, what the data says, and what still matters.

Davit Khaburdzania23 Oct 20266 min read

For most of my career, the first big decision on a new project was the stack. With coding agents writing the code, I think it has become one of the smaller ones. If you're asking what the best language for AI coding is, my answer is the one where an agent gets a clear pass or fail quickly, that has plenty of public code to learn from, and that you can still read when you review what it wrote. Plenty of languages pass that test. The research below shows real differences between them, and almost all of those differences come from feedback and tooling.

Fifteen years of picking stacks

I've written software professionally for more than 15 years, and the stack changed with almost every job. At Shogun, the Y Combinator page builder where I was the first engineering hire, it was Ruby on Rails and React. At Blocks I moved a major application from Rails to Elixir and Phoenix for performance and scale. EverAI, where I was the founding engineer, ran on Rails and React with LLM, image, voice and video APIs. TurbaMedia was Node.js, TypeScript and React, and Copia was TypeScript and Python. In between came React Native and a few years running an agency. The Experience section has the full list.

For most of that time the stack decided a lot: who you could hire, which libraries you got for free, and how fast the team could move in its first months. Switching languages had a real learning cost.

What changed with agents

Coding agents now write much of the code, in whatever language the project uses. Andrej Karpathy described going, within a few weeks of December 2025, from writing most of his code himself to having agents write almost all of it (Yahoo Tech). Simon Willison opened his Agentic Engineering Patterns guide with a chapter called "Writing code is cheap now". Armin Ronacher, who wrote Flask, put it as "the cost of coding is going down dramatically" (A Language for Agents).

My own work in 2026 covers a lot of stacks:

  • Rillow, a Next.js app.
  • Bundle, which I build alone: one repository with an iPhone app, an Android app for e-ink tablets, a Chrome extension, a backend and a website.
  • This site, plain HTML, CSS and JavaScript with no framework and no build step, plus Shiba Land, a small platformer in three.js.
  • TypeScript and Python at Copia.

The language for each one came from the platform and the product. An agent reads and writes all of them well enough that my time goes into deciding what each product should do.

The data says languages still differ

My claim has to deal with the evidence that languages are not equal for agents.

José Valim, who created Elixir, made the strongest case for one language in Why Elixir is the best language for AI. He cites Tencent's AutoCodeBench, which compared 20 languages across more than 30 models. Across all models, 97.5% of the Elixir problems were solved by at least one model, the highest of any language, and Claude Opus 4 scored 80.3% on Elixir, ahead of C# at 74.9% and Kotlin at 72.5%. His explanation is immutability, which keeps a function's effects visible without loading the code around it, and stability: Elixir has stayed on version 1.x since 2014, so old examples still work.

GitHub's Why AI is pushing developers toward typed languages cites a 2025 study that found 94% of compilation errors in LLM-generated code were type-check failures. TypeScript also became the most used language on GitHub in August 2025, ahead of Python and JavaScript.

Armin Ronacher's post names specific languages. Go works well for agents, he writes, because code is easy to grep, import cycles are forbidden and test results are cached, and he now uses TypeScript where he used to use Python. On the other side, he finds Swift's tooling painful enough that agents struggle, and Python's significant whitespace harder for an agent to edit cleanly.

Read together, these sources point at the same properties: fast, clear feedback, and code an agent can understand from a few files. Those come from the type checker, the compiler, the test runner and the project's conventions much more than from the syntax.

What still matters

The first thing I look at is whether an agent can check its own work. A type checker, a compiler that explains itself, tests that run in seconds and one command that says pass or fail do more for agent output than the choice between two languages. Armin's line is "The more uniform the tooling the better", and I agree with it. Even this site, which has no build step at all, has a check: a thread runs the site on a local server before a push and opens the live page after it.

Conventions matter for the same reason. Rails and Phoenix put files where an agent expects them, and a stable language means the examples the model learned from still compile. A codebase with five ways to do the same thing confuses an agent the way it confuses a new hire.

The platform still matters. An iPhone app goes through Xcode, signing and App Review whatever you write it in, and that tooling decides more about an agent's day than the language does.

And you still own what ships. Pick something you can read well enough to review, because you'll read far more code than you write.

So what is the best language for AI coding?

For a new project, I'd pick the language the platform expects and turn on the strictest checks the team can live with. For a web app that usually means TypeScript, because its type checker catches the kind of error the GitHub study found most often, and there is a huge amount of public TypeScript for models to learn from. If you love Elixir, Valim's numbers say agents do well there too. If your team already knows Rails, keep Rails and invest in tests. An agent can work in any of them. The thing it handles badly is a codebase with no way to check its work.

What this means if you hire engineers

Years in one framework tell you less than they used to. An engineer who works well with agents can get productive in an unfamiliar stack quickly, because the agent already knows it. What's harder to find is someone who breaks a feature into tasks an agent can finish, checks the result properly and decides what not to build. Those are the skills I'd interview for now.

Where I still choose carefully

Some code is still worth choosing a language for. Hot paths where performance is the product, native platform work, and very new frameworks with little public code are places where the choice still deserves time. Armin's note on Zig is a good example: it changes quickly and has little training data, so it works but isn't ideal. A large team on a long-lived codebase also gains more from consistency than from any single language feature.

For everything else, choose the stack that fits the platform, make the feedback loop fast, and spend the time you saved on the product. If you want to see how that works day to day, I wrote up my agentic coding workflow, and my CV has the rest of my background.
