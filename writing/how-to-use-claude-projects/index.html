How to use Claude Projects the right way

Claude Projects became a coordinator with threads in September 2026. How to set one up, write instructions, use memory and keep usage down.

Davit Khaburdzania23 Oct 202610 min read

If you're working out how to use Claude Projects well, treat a project as one stream of work that you brief once and keep feeding. Since the September 2026 redesign, a project is a conversation with a coordinator that starts a thread for each task, and every thread is a full Claude Code session. You get the most out of it by putting standing rules in the project instructions, letting memory collect your decisions, sending work as it comes up, and answering the threads that wait on you. I run this site, davit.cc, in a project, and the examples below come from it.

What changed in September 2026

Anthropic announced the change on September 17, 2026, in Projects redesigned: from folder to conversation. The older Projects in claude.ai chat were a folder: reference files, custom instructions and the chats you had inside it. The new Projects live in Claude Code. You talk to one coordinator in the project chat. It decides whether to answer you directly or start a thread, and each thread is a cloud session with its own branch and copy of the repository. Threads report back to the coordinator, read and add to a shared memory, and leave their files in the project's Library.

Some practical facts from the Claude Code docs, as of October 2026:

  • Projects are in public beta on the Pro and Max plans and are still rolling out. They aren't on Team or Enterprise yet.
  • You use them at claude.ai/code, in the Code tab of the desktop app, and in the mobile app, but not in the terminal CLI or the IDE extensions.
  • The older folder-style projects in claude.ai chat and Cowork keep working until the new version reaches them.

Several of the guides that rank for "how to use Claude Projects" still describe the folder version. Everything below is about the new one.

When a project is worth creating

A project pays off when the work has a goal that outlasts one session and keeps producing tasks. The docs give examples like one change across many repositories, an area you keep feeding bugs into, a migration bigger than a session, and work that isn't code at all, like a folder of contracts you keep asking questions about.

A single task that fits in one session is better as a plain cloud session. Work where every step needs your own machine fits a local session better. And a job that runs on a schedule with no conversation around it is a routine.

My personal site is that kind of stream. Since October 8 the davit.cc project has handled a full redesign, a new favicon, four small Playground experiments and these blog posts. None of that fits in one session, and all of it shares the same rules.

Let Claude propose the setup

I didn't write my setup from scratch. My first message in the new project was:

Help me set up this new project from my recent work. Look through my recent sessions and repositories, identify the main thread of work, and propose a project setup: a short name, the repositories it should include, an environment, concise project instructions drawn from what kept coming up, and one or two optional routines. Show me the proposal before changing anything.

Claude read my last 46 sessions from the previous four weeks, found the one line of work that belonged in this project (deploying davit.cc), and came back with draft instructions and an optional weekly health check of the live site. Nothing changed until I answered "yes". If you already have a cloud session doing the work, the "Continue as project" option in its menu does the same thing from that session.

Write project instructions threads can follow

Project instructions are the brief that every new thread and the coordinator start from, up to 16,000 characters. A good brief says what the project is for, where the work happens (repository, branch, how pull requests are named), how a thread checks its own work, what to do when something it needs is missing, and what needs your go-ahead.

Mine for davit.cc are one paragraph:

Site is davit.cc, built from the main branch of davit-khaburdzania.github.io and served by a Cloudflare Worker (wrangler.jsonc). Davit is the only one working on the site, so don't open pull requests: commit and push straight to main. Every push to main deploys davit.cc automatically within about a minute (Cloudflare's GitHub connection), so a push is a production change: show Davit a preview of visual changes before pushing. Keep profile details (location "Tbilisi, Georgia", website davit.cc) consistent across the site, GitHub and LinkedIn. Verify changes on the live site after each push.

The first version was wrong. It said the site is served from the master branch. The first thread read the repository and found a Cloudflare Worker serving the main branch, and a few minutes later the coordinator had fixed the instructions. The rule about pushing straight to main came a day later, when I told a thread to remember that I'm the only one working on the site and don't want pull requests. The rule about previews came right after, once we'd confirmed that every push deploys.

Two details are easy to miss. A change to the instructions reaches new threads only, so a thread that is already running keeps the old brief. And instructions are for rules. Facts about one repository, like build commands, belong in that repository's CLAUDE.md.

Instructions, memory and CLAUDE.md

A project carries context in three places, and each one has its own job:

Where What goes in it Example from davit.cc
Project instructions Rules every thread needs from its first message Push straight to main, and show a preview of visual changes first
Project memory Decisions and pitfalls Claude collects as you work "Pixel is better": the favicon and Pet the Shiba use the pixel-art Shiba
CLAUDE.md or AGENTS.md in the repository How the code is built and styled "Light only. Never use green accents."

Project memory is a set of files Claude writes itself. Every cloud thread reads the index file, MEMORY.md, when it starts and opens the other files when it needs them, and you can read and edit them in Project settings > Memory. You fill it by asking: "remember that Unposed goes last in the Projects list" is all it takes. In my project, memory holds the design decisions from the redesign, the fact that Paper only runs on my Mac, and the three topics I picked for this blog.

The repository file is the one I'd write first, because every session reads it, inside a project or not. My AGENTS.md is 64 lines on how the site is built, shipped and styled, and CLAUDE.md just points to it, so every thread and every other agent reads the same rules.

Send work, then walk away

Once the setup is in place, you write to the coordinator the way you'd write to a colleague. A quick question gets an answer in the chat. New work becomes a thread, or goes to a thread that's already working in that area, and several unrelated tasks in one message become separate threads. This blog started with one message from me, and the coordinator started a thread with the context from memory already attached: the three post topics I'd chosen two weeks before.

The Overview pane groups threads by state: Ready for review, Waiting on you, Working, Landing, Idle and Resolved. When a choice changes what I'm building, the thread asks on a card with two to four options and a recommendation. For my CV, the card asked whether Claude should edit the PDF or I'd export it myself, and I picked "I'll do it".

You can also tell the coordinator how to run the project, in plain words. The docs list examples like "Propose threads and wait for my go-ahead before starting them", "Run at most two threads at a time" and "Only post when something finishes or is blocked". Claude saves these to memory and follows them, though a thread limit given this way isn't enforced.

Approvals work in a way you might not expect. Threads run in auto mode, so most commands run without asking, but when a thread does need your approval, the prompt is inside that thread. Telling the coordinator "go ahead" doesn't reach it. Open the thread and answer there.

Run a thread on your own computer

Some work needs your machine: a local database, a device simulator, or an app that only runs on your laptop. For me that's Paper, the design tool I use, which only runs on my Mac. A project can run that one thread on your computer through Remote Control while the rest stay in the cloud.

To set it up in the desktop app, open Settings > Claude Code, turn on "Use this computer from your phone and claude.ai" and add the folder. Or run claude remote-control in the folder from a terminal. Both need Claude Code v2.1.280 or later. Then choose "Work locally" from the + menu in the project chat, describe the task, and allow it on the card.

A thread on your computer uses that machine's files, tools, MCP servers and settings. It starts with the project instructions but without the memory files, so anything it must know goes in the instructions or the task. It pauses while the computer sleeps.

Keep usage under control

A project uses your plan faster than a single session, because each thread is a full Claude Code session and several can run at once. A new project runs threads on Opus at high effort, and you can change the thread and coordinator models and effort in Project settings > General. There's also a hard limit of 200 new threads per day across your projects.

Long threads cost more than they look. The redesign thread grew to 165 replies over two days. When a thread has been idle longer than the cache lifetime (an hour on Pro and Max), a follow-up makes Claude re-read the whole conversation before it does anything. Now new work gets a fresh thread, and the redesign thread is resolved. Threads that watch a pull request also wake up when CI fails or a review comes in, so ask a thread to stop watching when you're done with it. The Usage tab in project settings shows where the tokens went, by thread and by model.

Frequently asked questions

When should I use a project instead of a chat?

Use a project when the work outlasts one session and keeps producing tasks, like a product, a migration or a site you keep improving. A one-off question fits a chat, and a single coding task fits one cloud session.

What is the difference between Claude Projects and Claude Code?

Projects are built on Claude Code. Every thread is a Claude Code session, usually in the cloud. The project adds the coordinator, shared instructions and memory, the Library of files, and the Overview pane that tracks every thread.

Can I share a Claude Project with my team?

Not during the beta. A project belongs to one person, and thread transcripts can't be shared. For a team giving Claude work together in Slack, Anthropic points to Claude Tag instead.

Do cloud threads get my local skills and MCP servers?

No. Cloud threads get the connectors on your claude.ai account, the skills you enable there, and the skills, agents and commands committed to the project's repositories. Anything installed only on your laptop is missing unless the thread runs on your computer.
